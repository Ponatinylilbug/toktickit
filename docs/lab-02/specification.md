# Lab 2 Sprint Engineering Specification: TokTickIT Requester Ticketing MVP with UI Foundation

## 1. Sprint Goal
Deliver a responsive, user-friendly Requester-facing MVP for TokTickIT using the **Zen Green Theme**. A Requester can simulate logging in via a Development Requester selector, create IT support tickets with permitted attachments, receive a unique backend-generated Ticket Number, view and paginate through their own tickets in My Tickets (with search, filter, and sort), view Ticket Details as read-only, and manage attachments with strict soft-removal rules.

---

## 2. Stakeholder Request Interpretation
The IT department needs an end-user ticketing interface allowing staff/students to report IT issues, specify priority and affected systems, upload supporting evidence, and track submitted requests. To facilitate early testing before real authentication is delivered in Lab 3, a Development Requester selector will simulate user identities. Strict data isolation ensures users only see and manage their own tickets and attachments.

---

## 3. Scope

### 3.1 Included Scope
- **Development Requester Selector:** Simulated user context switcher loading active Requesters from PostgreSQL.
- **Create Ticket Screen:** Responsive form to input Category, Related System, Requested Priority, Summary, Description, and initial attachments.
- **Ticket Number Generation:** Unique, standardized official ticket numbering assigned upon successful creation.
- **My Tickets Screen:** Requester-isolated paginated ticket list supporting text search, category/priority/status filters, multi-column sorting, and empty/error states.
- **Requester Ticket Detail Screen:** Read-only view of ticket details and attachment management (view active metadata, download active files, upload new attachments, and soft-remove existing attachments with a required reason).
- **Attachment Constraints & Lifecycle:** File type validation (JPG, JPEG, PNG, WEBP, PDF), 5MB size limit, max 5 active attachments per ticket, and soft-removal preventing file downloads while preserving audit metadata.
- **Zen Green UI Theme:** Comprehensive styling tokens, consistent layout rules across Desktop, Tablet, and Mobile.

### 3.2 Explicitly Excluded Scope
- Real authentication, passwords, sessions, JWTs, and role-based permissions (deferred to Lab 3).
- IT Staff queues, ticket assignment, IT Priority adjustments, and status workflows beyond `New`.
- Public Comments, Internal Notes, and Actions Taken.
- Administrative CRUD interfaces for categories, systems, and users.

---

## 4. Functional Requirements

- **FR-01 (Development Requester Context):** The user can select an active Requester from a dropdown to establish the testing context. The selected user identity is persisted across views and displayed in the application header.
- **FR-02 (Reference Data Retrieval):** The application loads active Categories and Related Systems from the database to populate dropdown controls.
- **FR-03 (Ticket Submission):** The user can submit a ticket with required details and optional valid attachments. Upon submission, form input is validated on both client and server.
- **FR-04 (Ticket Number Assignment):** Backend assigns a unique `ticketNumber` formatted as `TKT-YYYY-XXXXXX` upon creation.
- **FR-05 (My Tickets Retrieval):** The user can view a paginated list of tickets owned exclusively by the currently selected Requester.
- **FR-06 (Search, Filter, Sort, Pagination):** The ticket list supports keyword search on summary/description/ticket number, filtering by Category, Priority, and Status, sorting by date/number/priority, and page navigation with configurable page size.
- **FR-07 (Ticket Detail Inspection):** The user can view the complete read-only details of an owned ticket. Direct access attempts to unowned tickets are blocked with HTTP 403/404.
- **FR-08 (Attachment Upload):** The user can upload valid attachments during ticket creation or directly from the Ticket Detail screen (up to 5 active files).
- **FR-09 (Attachment Download):** The user can download active attachments.
- **FR-10 (Attachment Soft-Removal):** The user can soft-remove an owned attachment by providing a removal reason. The record remains visible with removal metadata, but the file content becomes inaccessible for download.

---

## 5. Business Rules

- **BR-01 (Ticket Number Uniqueness):** The official Ticket Number is generated by the backend upon ticket creation using the pattern `TKT-YYYY-XXXXXX` (where `YYYY` is the current year and `XXXXXX` is a sequential or unique numeric identifier).
- **BR-02 (Initial Ticket Status):** All newly created tickets are automatically initialized with Current Status `New`.
- **BR-03 (Development Testing Identity):** The Development Requester selector is strictly a temporary testing mechanism and not secure authentication.
- **BR-04 (Active Requesters Only):** The Development Requester selector only lists active requesters (`isActive: true`). Inactive requesters cannot be selected or used to create tickets.
- **BR-05 (Data Ownership Isolation):** A Requester can only view, search, and manage tickets where `requesterId` matches their currently selected ID. Requests for tickets belonging to another requester must be rejected.
- **BR-06 (Ticket Summary Constraints):** Ticket Summary is required, whitespace-trimmed, and must be between 5 and 100 characters.
- **BR-07 (Description Constraints):** Description is required, whitespace-trimmed, and must be between 10 and 2000 characters.
- **BR-08 (Category & Related System Requirement):** Every ticket must reference a valid, active `CategoryId` and `RelatedSystemId`.
- **BR-09 (Requested Priority Defaults):** Requested Priority must be one of `LOW`, `MEDIUM`, `HIGH`, or `URGENT`. Default is `MEDIUM`.
- **BR-10 (Permitted Attachment Formats):** Only files with MIME types `image/jpeg` (jpg/jpeg), `image/png` (png), `image/webp` (webp), and `application/pdf` (pdf) are accepted.
- **BR-11 (Attachment File Size Limit):** Maximum file size is 5 MB (5,242,880 bytes) per attachment. Oversized files must be rejected immediately with clear feedback.
- **BR-12 (Attachment Count Limit):** A single ticket cannot have more than 5 active (non-removed) attachments at any time.
- **BR-13 (Soft-Removal Rule):** When an attachment is removed, its record is marked `isRemoved = true`, recording `removedAt` timestamp and `removalReason`. Removed attachments remain listed in the UI metadata as "(Removed)", but file download and preview are strictly prohibited.
- **BR-14 (Form Error State Retention):** If ticket submission fails due to validation errors or backend disconnection, the entered form data must be retained so the user does not lose their input.
- **BR-15 (Default Ticket Sorting):** By default, My Tickets displays records ordered by `createdAt` DESC, with secondary order `ticketNumber` DESC.

## 7. Data Changes & Prisma Schema

### 7.1 Entity Models
- **`RequesterUser`**: Simulated requester accounts with fields `id`, `name`, `email`, `department`, `isActive`, `createdAt`, `updatedAt`.
- **`Category`**: Ticket categories (`Account and Access`, `Hardware`, `Software`, `Network`) with `id`, `name`, `isActive`.
- **`RelatedSystem`**: IT services/devices (e.g., `Email`, `Campus Wi-Fi`, `VPN`, `LEB2 App`, `Grade Submission App`, `Printer`, `Corporate Laptop`) with `id`, `name`, `isActive`.
- **`Ticket`**: Support requests with `id`, `ticketNumber` (unique), `summary`, `description`, `requestedPriority`, `currentStatus` (default `NEW`), `requesterId`, `categoryId`, `relatedSystemId`, `createdAt`, `updatedAt`.
- **`Attachment`**: File metadata with `id`, `ticketId`, `fileName`, `originalName`, `fileSize`, `mimeType`, `filePath`, `isRemoved` (default `false`), `removedAt`, `removalReason`, `createdAt`.

### 7.2 Seed Data Specifications
- 4 Ticket Categories.
- At least 6 realistic Related Systems.
- At least 4 active `RequesterUser` records and 1 inactive `RequesterUser` record.
- Idempotent execution (safe to run repeatedly via `prisma db seed` without duplicates).

## 8. API Contract Summary
- `GET /api/requesters` - List active Development Requesters.
- `GET /api/categories` - List active Categories.
- `GET /api/related-systems` - List active Related Systems.
- `POST /api/tickets` - Create a ticket with validation and optional attachments.
- `GET /api/tickets` - Query tickets owned by active Requester with pagination, search, filter, and sorting.
- `GET /api/tickets/:id` - Fetch details for an owned ticket.
- `POST /api/tickets/:id/attachments` - Upload an attachment to an existing ticket.
- `GET /api/attachments/:id/download` - Download an active attachment file.
- `PATCH /api/attachments/:id/soft-remove` - Soft-remove an attachment with reason.

## 9. Acceptance Criteria (Given-When-Then)

- **AC-01 (Create Valid Ticket):** Given an active Requester is selected and valid ticket fields are filled, when the user submits the form, then a new ticket is saved in the database, a unique Ticket Number is returned, and a success confirmation is displayed.
- **AC-02 (Create Ticket Validation Failure):** Given the Create Ticket form is empty or contains summary < 5 chars, when the user clicks Submit, then field-level validation messages appear next to invalid controls and no API request is sent.
- **AC-03 (Attachment Upload on Create):** Given a valid PDF or image file (≤ 5MB), when attached to a new ticket and submitted, then the file is stored safely and associated with the ticket.
- **AC-04 (Invalid Attachment Rejection):** Given a file exceeding 5MB or with an unsupported extension (e.g., `.exe`), when selected, then an immediate validation error is shown and submission is prevented.
- **AC-05 (Max Attachment Limit):** Given a ticket already having 5 active attachments, when the user attempts to add a 6th attachment, then the system blocks the upload with an explicit error message.
- **AC-06 (Requester Selector Display):** Given the application loads, when the Requester dropdown is rendered, then only active Requesters are shown and inactive Requesters are omitted.
- **AC-07 (Requester Context Switching):** Given Requester A is selected with tickets and the user switches to Requester B, when My Tickets is viewed, then only Requester B's tickets are displayed and Requester A's tickets disappear.
- **AC-08 (My Tickets Pagination & Search):** Given a Requester has multiple tickets, when a search term is entered or page 2 is clicked, then the list updates with matching records and accurate pagination counts.
- **AC-09 (Ticket Detail Read-Only View):** Given an owned ticket is opened in Ticket Detail, then all ticket header fields are displayed in read-only format alongside active and soft-removed attachments.
- **AC-10 (Unauthorized Ticket Access):** Given Requester A is active, when requesting the detail or attachments of a ticket owned by Requester B, then the backend rejects the request with HTTP 403/404.
- **AC-11 (Attachment Download Active):** Given an active attachment, when the user clicks Download, then the file is delivered with the original filename.
- **AC-12 (Attachment Soft-Removal):** Given an active attachment on an owned ticket, when the user confirms soft-removal with a reason, then the attachment is marked as removed, metadata displays the reason and timestamp, and download is disabled.
- **AC-13 (Blocked Download for Removed File):** Given a soft-removed attachment, when a download request is attempted, then the backend responds with HTTP 404/410 and file delivery is refused.
- **AC-14 (Form Error Retention on Network Failure):** Given the backend is unavailable or returns 500 during submission, when the request fails, then a user-friendly error banner is shown and entered form fields remain intact.
- **AC-15 (Responsive Navigation & Layout):** Given any screen size (Desktop ≥992px, Tablet 768-991px, Mobile <768px), when the user interacts with tickets and forms, then all controls remain legible, unclipped, touch-friendly, and without horizontal overflow.

## 11. Assumptions and Architectural Decisions
1. **Attachment Storage:** Attachments are stored on local disk under `server/uploads/` using UUID-prefixed safe filenames to prevent path traversal and collisions, while retaining `originalName` in the database.
2. **Soft-removal strategy:** Physical files of soft-removed attachments are retained on disk for audit compliance, but API-level checks disallow access and streaming if `isRemoved === true`.
3. **Client-side Session Simulation:** The active Requester ID is stored in React state / localStorage to preserve context during development testing across page refreshes.
